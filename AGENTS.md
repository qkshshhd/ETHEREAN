Read `Docs/References/ETHEREAN_Codex_Collaboration_Prompt.md` and the relevant sections of `Docs/References/ETHEREAN_GDD.md` before making changes. These preserve the complete user-provided master prompt and the complete extracted text of the 34-page GDD uploaded on 2026-10-22. PDF images and layout are not reproduced; reopen the source attachment for visual references. The master prompt mentions an older PDF suffix; the supplied GDD (2) is the reference snapshot here.

- The user is the technical decision maker and final reviewer. User update (2026-11-02): increase daily workload and use larger cohesive review units. One explicitly approved unit may include related features, Inspector/scene connections, tests and reporting needed for a playable result (for example, one complete attack cycle). Agree the bundle scope before implementation; complete and explain it, then stop for review. This does not authorize unrelated features, the full roadmap, skipping checks, commit or push. See the latest revision in Docs/Plans/ETHEREAN_Daily_Plan_2026-11-08.md.
- Before editing, inspect Git status, applicable AGENTS.md files, existing code, Unity version, packages, scenes, prefabs, Input Actions, and assembly definitions. Preserve existing uncommitted work, .meta files, and GUIDs. Do not commit, push, upgrade packages, or replace project architecture without authorization.
- Follow SOLID proportionately. Prefer composition, encapsulation, and small responsibilities. Avoid speculative interfaces, giant controllers, and several components overwriting Rigidbody2D velocity.
- Use existing namespaces (`Etherean.Player`, etc.). Serialized fields use camelCase, public types/methods/properties use PascalCase, and existing nonserialized private fields use _camelCase. Avoid unnecessary comments and FormerlySerializedAs attributes.
- Latest explicit user decisions take priority. Distinguish confirmed GDD requirements from proposals and temporary tuning values. Report document conflicts before changing affected behavior.
- Use New Input System. Generate scenes and prefabs through Unity Editor APIs where possible, and connect Inspector references.
- Run appropriate Unity compilation and behavior checks when available. Distinguish completed, incomplete, and unverified work; never claim a test was run when it was not.
- After each feature, report changed/added files, actual execution flow, design reasons and tradeoffs, test evidence, exact editor reproduction steps, temporary values and limitations. Provide measured performance numbers only when actually measured.
- Scope of the vertical slice: prologue through the first forest exit. No automatic implementation of the full roadmap.

## Mandatory change report

사용자 재확인 사항 (2026-10-26): 모든 작업이 끝나면 사용자가 직접 변경을 이해하고 검토할 수 있도록 아래 항목을 반드시 보고한다. 코드 구현뿐 아니라 버그 수정, 씬·프리팹·에셋 연결, 디자인·VFX 및 문서 변경에도 적용한다.

1. **수정한 파일:** 파일별 전체 경로와 수정 위치를 적는다. 코드는 클래스·메서드·필드 이름, 씬·프리팹은 오브젝트·컴포넌트·Inspector 항목, 문서는 제목·구역으로 정확히 식별한다. 파일명만 나열하지 않는다.
2. **추가한 파일:** 파일별 전체 경로, 생성 목적, 담당 기능과 다른 파일과의 연결을 설명한다. 추가 파일이 없으면 없다고 명시한다. 삭제하거나 이름을 바꾼 파일이 있으면 함께 보고한다.
3. **변경 전후와 이유:** 각 변경이 기존 동작을 어떻게 바꾸며 왜 필요한지 설명한다. 신규 파일은 무엇을 책임지고 어디에서 호출되거나 사용되는지 설명한다.
4. **실제 동작 원리:** 입력·이벤트부터 관련 클래스와 메서드, 상태 전환, 이동·판정·표시 결과까지 실행 순서를 사용자가 이해할 수 있게 설명한다. 설계 이유와 중요한 트레이드오프를 포함한다.
5. **연결과 직접 확인:** 관련 씬·프리팹·Inspector 연결과 사용자가 직접 확인할 순서 및 예상 결과를 적는다. 해당하지 않는 항목을 억지로 만들지 않는다.
6. **검증과 남은 사항:** 실제 실행한 검사와 결과, 미검증 항목, 임시값 및 제한을 구분한다. 컴파일 통과를 실제 동작 검증으로 바꾸어 표현하지 않는다.
7. **마무리 보고:** 최종 답변에 최소한 파일별 변경 위치와 역할을 요약한다. 상세 보고서 링크만 제공하고 설명을 생략하지 않는다. 기능 단위의 상세 기록은 협업 마스터 프롬프트의 9개 보고 항목을 따른다. 사용자 리뷰와 승인 전에는 다음 기능으로 넘어가지 않는다.
